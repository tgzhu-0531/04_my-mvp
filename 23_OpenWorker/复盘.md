## 五、经验教训与总结

### 🟢 做得好的

1. **服务端实现完整** — 首次交付的 FastAPI 后端 9 个 API 端点全部通过验证，SQL 参数化防护、CORS 配置、异常处理均到位
2. **数据库设计规范** — 5 张表关系完整，外键约束 + 字段约束（CHECK）+ 唯一索引数据完整性
3. **前端覆盖 4 个 Tab 全功能** — 总览统计/图表、三维筛选查询、多城市对比、来源全追溯，功能闭环完整
4. **文档齐全** — README、数据源清单、已知限制、复盘报告一应俱全
5. **编码问题修复及时** — GBK 编码、FastAPI 弃用警告、数据库去重均在发现后立即修复

### 🔴 做得不够的

1. **⛔ 没有在开工前读参考项目** — 同目录已有 8 个完成项目，它们的代码风格/架构/图表/数据范围明确可查，但我跳过了这一步。这是所有方向性错误的根源
2. **⛔ 数据范围错误** — 用 10 城市替换了 PRD 明确的 5 省（粤/苏/鲁/浙/蒙）
3. **⛔ PDF 读不全后没有追问** — PRD 关键字段无法解码时，应该向您确认而不应自行假设
4. **⛔ 第一版选了完全不同的技术栈** — FastAPI + ECharts 与同目录项目（静态 JSON + Chart.js）不一致，导致全面重写
5. **⛔ 更新入口描述时没比对相邻条目** — 写的"10 个主要城市"就在"5 省（粤/苏/鲁/浙/蒙）"旁边

### 📈 后续改进建议

1. **开工前 3 分钟黄金检查**：
   - 读一个已完成项目的代码 → 确认架构模式
   - 读总览页的 PROJECTS 数组 → 确认数据范围和描述格式
   - 确认项目目录结构 → 确认部署规范

2. **PDF 解码的策略**：遇到 CID 字体 + 双重压缩编码的 PDF，如果 60 秒内未能提取正文，应立即转向"向用户询问关键需求"而非自行推断

3. **"活文档"优先原则**：当上游文档（PRD PDF）不可信赖时，下游代码（同目录已部署项目）是最可靠的"活文档"。代码不会撒谎，风格不会漂移

4. **修改时扫一眼周围代码**：在 `index.html` 的 `PROJECTS` 数组中改一个条目时，先看上下 3 行的格式和数据，确保对齐

5. **Windows 环境工具箱**：
   - ❌ 不用 `&&` / `mkdir -p` / `head` / `tail`
   - ✅ 用 `powershell -Command "..."` 执行复杂命令
   - ✅ 路径带空格必须用引号包裹
   - ✅ Python 脚本写入文件再执行，不在 shell 中 inline 多行代码
   - ✅ `sys.stdout.reconfigure(encoding='utf-8')` 解决 GBK 报错
