### 详细步骤清单

#### 步骤 1：PRD 理解与需求拆解（11:00 - 11:05 | ~5 min）

- 🧠 **大模型推理**：读取 PDF 文档后理解 16 个章节需求，识别核心约束——5 省数据范围、双数据源架构（SQLite/CSV）、禁止编造数据、口径统一要求、数据追溯、总览页接入，以及拒绝使用 mock 数据的底线规则。
- 🤖 **Agent 执行**：调用 `pdf` skill 读取 PDF 文件 → 因文件过大改用 `Read` 读取 Markdown 版本 → 调用 `TodoWrite` 建立任务清单。

#### 步骤 2：公开数据检索与采集（11:05 - 11:20 | ~15 min）

- 🧠 **大模型推理**：判断各省分时电价政策差异（广东有尖峰且仅 7-9 月、山东设有尖峰/深谷、浙江 2026 年 7 月新政策浮动倍率扩大等），交叉验证各来源可靠性和口径一致性，决定采用 5 级标准分类（尖峰/峰/平/谷/深谷）统一各省时段命名差异。
- 🤖 **Agent 执行**：`WebSearch` × 4 次搜索广东、江苏、山东、浙江、内蒙古分时电价政策 → `WebFetch` × 2 次获取政策原文页面 → 额外 `WebSearch`/`WebFetch` 交叉验证口径。

#### 步骤 3：数据建模与项目结构搭建（11:20 - 11:29 | ~9 min）

- 🧠 **大模型推理**：设计 5 表关系模型（regions/policies/periods/data_sources/missing_records），定义外键约束和标准分类编码规则，决定 CSV 文件结构与 SQL 建表语句一一对应以保证双向导入导出兼容。
- 🤖 **Agent 执行**：`Write` 创建 `01_init.sql`（23 条 SQL 定义）→ `Write` 创建 `config.json` 双数据源配置 → `Write` × 5 创建 5 个 CSV 数据文件 → `RunCommand` 清理并重建目录结构。

#### 步骤 4：后端服务开发（11:29 - 11:30 | ~5 min）

- 🧠 **大模型推理**：设计 7 个 RESTful API 端点（regions/sources/policies/periods/missing/overview/daily-curve），选择 better-sqlite3 同步驱动简化本地开发，配置端口 3456 避免与常见端口冲突。
- 🤖 **Agent 执行**：`Write` 创建 `server/server.js`（Express 服务入口）→ `Write` 创建 `server/db.js`（数据库访问层）→ `Write` 创建 `server/package.json` → `Write` 创建 `scripts/import_csv_to_sqlite.py` 和 `export_sqlite_to_csv.py`。

#### 步骤 5：前端开发（11:30 - 11:29 | ~35 min）

- 🧠 **大模型推理**：选择纯静态 SPA 架构以同时支持 IIS/Pages 静态部署和 SQLite 本地验证；选择 Chart.js 轻量图表库；设计 8 个功能模块（概览/统计/价格表/结论/图表/省份卡片/数据源/缺失信息/方法说明），实现配置驱动的数据加载器，避免模式写死。
- 🤖 **Agent 执行**：`Write` 创建 `index.html`（200+ 行 SPA 主页面）→ `Write` 创建 `css/style.css`（700+ 行响应式样式）→ `Write` 创建 `js/config.js`（配置加载模块）→ `Write` 创建 `js/data-loader.js`（双模数据加载器）→ `Write` 创建 `js/chart.js`（24h 五省叠图绘制）→ `Write` 创建 `js/app.js`（主应用逻辑）。

#### 步骤 6：文档编写（11:29 - 11:34 | ~18 min）

- 🧠 **大模型推理**：判断需要 4 份独立文档覆盖不同读者需求——README 面向开发者（启动/切换/初始化）、DATA_DICTIONARY 面向维护者（表结构/字段/编码）、DATA_SOURCES 面向审核者（来源 URL/可靠性/采集时间）、KNOWN_LIMITATIONS 面向用户（已知限制/改进方向）。
- 🤖 **Agent 执行**：`Write` 创建 `README.md` → `Write` 创建 `DATA_DICTIONARY.md` → `Write` 创建 `DATA_SOURCES.md` → `Write` 创建 `KNOWN_LIMITATIONS.md`（4 份文档共约 1000 行）。

#### 步骤 7：总览页接入与测试（11:29 - 11:34 | ~10 min）

- 🧠 **大模型推理**：依据 PRD §11 要求，识别根目录总览页需要更新的三个位置（状态标签从"待部署"改为"已部署"、说明文案改为真实交付摘要、按钮改为访问入口），同时确保子项目页面添加"返回总览页"链接。
- 🤖 **Agent 执行**：`Read` 根目录 `index.html` → `SearchReplace` 更新 TRAE Work 卡片（状态标签 + 说明文案 + 按钮）→ `SearchReplace` 在子项目 `index.html` 添加返回链接 → `RunCommand` 启动 Python HTTP 服务器 → `run_mcp` (browser_snapshot) 截图验证 → `run_mcp` (browser_click) 验证导航。

#### 步骤 8：SQLite 排错修复（11:34 - 11:53 | ~19 min）

- 🧠 **大模型推理**：诊断 SQLite 模式报错——排查链路为"数据库文件存在 → 表结构正确 → 核心表为空 → 导入脚本执行失败 → 外键约束失败 → CSV 列错位"，逐层缩小根因范围，最终定位到 `policies.csv` 中 4 行数据因多余逗号导致列偏移。
- 🤖 **Agent 执行**：`LS`/`Read` 检查文件结构与数据库 → `RunCommand` 运行 Python 脚本检查数据库 → 反复运行调试脚本定位具体错误行 → `SearchReplace` × 4 修复 `policies.csv` 中多余逗号 → 重新导入数据库（123 行全部成功）→ `RunCommand` 执行 `npm install` 安装依赖 → 启动后端服务 → `curl.exe` 验证 5 个 API 端点。

#### 步骤 9：模式标识修复（11:53 - 12:00 | ~7 min）

- 🧠 **大模型推理**：发现配置 `sqlite` 但页面显示 CSV 的根因是 3 处静态文本硬编码（`data-loader.js` 误导性参数 `loadData('csv', ...)`、`index.html` 方法卡片固定写死"CSV 模式"、错误提示固定说"CSV 文件缺失"），决定实施 3 层模式标识方案确保配置与显示 100% 一致。
- 🤖 **Agent 执行**：`Read` × 4 排查代码 → `SearchReplace` 修复 `data-loader.js` 误导参数 → `SearchReplace` 修复 `index.html` 方法卡片硬编码 → `SearchReplace` 修复错误提示 → `SearchReplace` 新增 `style.css` 3 层模式标识样式 → `SearchReplace` 新增 HTML 结构 → `SearchReplace` 更新 `app.js` 动态渲染逻辑 → `curl.exe` 验证 API + `OpenPreview` 验证页面。

## 五、经验教训与总结

### 🟢 做得好的

1. **完整覆盖 PRD 全部 16 个章节需求**：从数据范围、来源规则、口径要求、双数据源架构、数据建模、网站功能、部署编码、总览页接入到交付物和验收标准，全部达标。24 个交付文件结构清晰，职责分明。

2. **数据质量可控**：71 条分时时段记录全部来自 9 个可验证的公开来源（省级发改委/电网官网），8 条缺失记录均标注了检索过程和判断依据，严格区分真实数据、缺失数据和待验证数据，未出现编造数据的行为。

3. **配置驱动的双数据源架构**：同一套代码通过 `config.json` 配置驱动，同时支持 CSV 静态展示（IIS/Pages）和 SQLite 数据库验证（本地 npm start）两种场景，3 层模式标识确保了配置与显示的一致性。

4. **排错链路清晰**：面对 SQLite 模式报错，采用"数据库存在 → 表结构正确 → 数据行数 → 具体行内容"的逐层排查策略，最终定位到 CSV 文件中 4 行多余逗号这一隐蔽根因，展现了系统化的故障诊断能力。

### 🔴 做得不够的

1. **CSV 数据质量前置验证不足**：`policies.csv` 中 4 行数据因多余逗号导致列错位，这一缺陷在首次创建时未被发现，直到用户切换到 SQLite 模式报错后才被定位修复。如果能在首次创建 CSV 时就进行列数校验，可节省约 19 分钟的排错时间。

2. **模式相关文本存在 3 处静态硬编码**：`data-loader.js` 中的 `loadData('csv', ...)` 误导性参数、`index.html` 方法卡片固定写死"CSV 模式"、错误提示固定说"CSV 文件缺失"——这 3 处静态文本硬编码导致配置 `sqlite` 但页面仍显示 CSV 的显示不一致问题，暴露了配置驱动架构实现中的代码审查不充分。
