## 五、经验教训与总结

### 🟢 做得好的

1. **双模式架构一次成型** — CSV/SQLite 适配器模式设计正确，`config.json` 驱动切换，前端读取配置并自动选择数据源，符合 PRD 第 7 条要求，未走弯路。

2. **数据与展示严格分离** — 价格数据独立存放于 CSV 和 SQL 文件，前端只读不写；真实数据、缺失数据、标准分类/原始名称双存储，便于后期维护和数据追溯。

3. **问题修复有策略性升级** — 从 R4（替换占位符）→ R7（改为首页+搜索指引），体现对政府网站 URL 不稳定性的深度理解，修复策略逐轮迭代优化。

4. **文档配套完整** — glossary / data_source_manifest / known_issues / README 四件套齐全，数据源可信度三级体系设计合理。

### 🔴 做得不够的

1. **路径计算过于依赖手动推算** — 4 层嵌套目录下，返回按钮路径修了 3 轮才正确（`../` → `../../` → `../../../`）。应在首次设计时就写出完整路径映射表或使用绝对路径参考。

2. **数据源 URL 未经预检** — 写入时直接使用占位符和假设路径，导致 R4/R7 两轮连续修复。应在首次写入前就用 `web_fetch` 验证所有外部链接的可用性。

3. **首页对比分析深度不够** — PRD 第 12 条要求"一句话分析结论"和"峰谷价差显性标注"，MVP 首页虽展示了 5 省数据，但分析结论偏弱，更多是展示而非解读。

4. **编码问题未在项目启动时统一规范** — 直到 R6 才发现并修复编码一致性问题，应在首次所有文件写入时就用脚本统一 UTF-8 无 BOM。

### 📈 后续改进建议

1. **建立路径映射表** — 对多层嵌套项目，在 README 或设计文档中标注所有文件间的相对路径关系，避免手动推算。

2. **外部链接预检流程** — 所有 CSV / 文档中的外部 URL 在首次写入前用脚本批量验证，将"首页+搜索指引"作为默认策略，避免两轮返工。

3. **首页分析增强** — 增加峰谷价差自动计算与展示、各省时段分布热力图、一句话 AI 分析结论区域，让首页真正辅助决策而非罗列数据。

4. **编码规范启动脚本** — 项目初始化时即运行统一 UTF-8 编码检查和转换，防止跨编辑器乱码。

5. **结构化采集过程记录** — 增加 `data_collection_notes.md`，记录每个数据源的检索过程、判断依据、遇到的问题，便于后续人工复核和增量更新。

6. **相对路径自动化检查** — 写一个脚本扫描所有 `.html` / `.md` 中的 `href` / `src`，验证目标文件是否存在，避免断链。
